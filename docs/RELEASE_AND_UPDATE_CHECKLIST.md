# چک‌لیست اجباری ساخت، آزمون و انتشار فیت‌یار

این سند مرجع هر انتشار APK است. در هر نسخهٔ جدید باید این فایل همراه با شمارهٔ نسخه، نتیجهٔ آزمون‌ها، اثرانگشت گواهی و لینک/شناسهٔ Artifact به‌روزرسانی شود. هیچ APK صرفاً به دلیل موفقیت ساخت، «آمادهٔ انتشار» محسوب نمی‌شود.

## ۱. هویت بسته، نسخه و سازگاری نصب

- [ ] شناسهٔ بستهٔ نسخهٔ اصلی دقیقاً `com.cognitivekernel.androidfit` است؛ برای انتشار عادی آن را تغییر نده.
- [ ] `versionCode` از آخرین نسخهٔ توزیع‌شده بزرگ‌تر است؛ هرگز آن را تکرار یا کم نکن.
- [ ] `versionName` متناسب با تغییرات افزایش یافته و با نسخهٔ ثبت‌شده در گزارش انتشار یکسان است.
- [ ] APK اصلی را با APK جداگانهٔ تست اشتباه نگیر: بستهٔ `com.cognitivekernel.androidfit.test2` فقط برای نصب کنار نسخهٔ اصلی است و به‌روزرسانی نسخهٔ اصلی نیست.
- [ ] پیش از توزیع، نام بسته، versionCode و versionName را از خود APK با ابزارهای Android SDK بررسی کن.
- [ ] قبل از هر آزمون نصب روی دستگاه دارای اطلاعات واقعی، از داده‌ها پشتیبان بگیر و امکان بازیابی را بررسی کن.

## ۲. امضای APK — شرط مسدودکنندهٔ انتشار

- [ ] هر نسخهٔ قابل نصب روی نسخهٔ قبلی باید با همان کلید و گواهی انتشار قبلی امضا شود.
- [ ] کلید خصوصی، رمزها یا فایل keystore هرگز وارد Git، Artifact عمومی، Issue یا لاگ نشوند.
- [ ] از Secretهای GitHub Actions استفاده کن: `FIT_YAR_RELEASE_KEYSTORE_BASE64`, `FIT_YAR_RELEASE_KEY_ALIAS`, `FIT_YAR_RELEASE_STORE_PASSWORD`, `FIT_YAR_RELEASE_KEY_PASSWORD`.
- [ ] فایل keystore را از Base64 بازسازی کن و خالی نبودن آن را بررسی کن؛ هیچ مقدار محرمانه‌ای چاپ نکن.
- [ ] با `keytool` گواهی keystore و با `apksigner verify --print-certs` گواهی APK نهایی را بررسی کن.
- [ ] اثرانگشت SHA-256 گواهی APK را با اثرانگشت کلید پایدار ثبت‌شده مقایسه کن. در صورت نبودن مقدار مرجع یا هرگونه عدم تطابق، انتشار را متوقف کن.
- [ ] اثرانگشت به‌تنهایی جای آزمون نصب را نمی‌گیرد. روی دستگاه آزمایشی تأیید کن که APK واقعاً روی نسخهٔ فعلی نصب می‌شود و برنامه پس از نصب اجرا می‌شود.
- [ ] کلید جدید یا debug key تولیدشدهٔ خودکار را جایگزین کلید انتشار نکن. اگر امضا عوض شده، APK را به‌عنوان به‌روزرسانی سازگار معرفی نکن.

## ۳. محتوای کتابخانهٔ تصویری حرکات

- [ ] فایل‌های GIF مورد انتظار در `app/src/main/assets/exercises` موجودند و در APK نهایی نیز بسته‌بندی شده‌اند.
- [ ] فهرست/کاتالوگ نام حرکات با نام فایل‌های GIF هماهنگ است؛ نام فایل‌ها به‌تنهایی اثبات نمی‌کند که حرکت درست به GIF متصل شده است.
- [ ] نگاشت هر حرکت به GIF را بررسی کن؛ مورد نامشخص یا تطبیق حدسی را منتشر نکن.
- [ ] در رابط فارسی، نام حرکت‌ها فارسی و خوانا باشد؛ در رابط انگلیسی، نام انگلیسی نمایش داده شود.
- [ ] حداقل چند حرکت از ابتدا، میانه و انتهای فهرست را باز کن و درست بودن GIF، نام، عنوان و اطلاعات حرکت را بررسی کن.
- [ ] اندازهٔ APK و شمار فایل‌های داخل آن را با نسخهٔ قبلی مقایسه کن؛ افزایش حجم به‌تنهایی اثبات وجود GIFهای جدید یا اتصال درست آن‌ها نیست.

## ۴. آزمون رگرسیون منوی کتابخانه و GIF

این مورد برای جلوگیری از تکرار باگ بسته‌شدن منو اجباری است:

- [ ] صفحهٔ کتابخانهٔ تصویری حرکات را باز کن.
- [ ] جست‌وجو یا پیمایش فهرست را انجام بده و یک حرکت را انتخاب کن.
- [ ] جزئیات/GIF حرکت باز شود، بدون آن‌که وضعیت صفحهٔ کتابخانه از بین برود.
- [ ] GIF را ببند؛ باید دوباره همان فهرست کتابخانه نمایش داده شود، نه منوی اصلی.
- [ ] وضعیت جست‌وجو و موقعیت پیمایش تا حد امکان حفظ شود.
- [ ] این مسیر را برای چند حرکت و پس از برگشت از جزئیات تکرار کن.
- [ ] رفتار دکمهٔ Back اندروید و دکمهٔ بستن داخل صفحه را جداگانه بررسی کن.
- [ ] پس از نصب APK به‌روزرسانی‌شده، این آزمون را روی دستگاه واقعی یا شبیه‌ساز انجام بده؛ آزمون ساخت به‌تنهایی کافی نیست.

## ۵. آزمون‌های اجباری پیش از ارائهٔ لینک

- [ ] Unit tests موفق.
- [ ] Lint موفق یا تمام هشدارهای باقیمانده بررسی و ثبت شده‌اند.
- [ ] Instrumented tests موفق؛ اگر محیط شبیه‌ساز شکست خورد، علت را مشخص کن و نتیجه را به‌اشتباه «موفق» ثبت نکن.
- [ ] APK اصلی با بسته و امضای درست ساخته شده است.
- [ ] امضا و گواهی APK نهایی تأیید شده‌اند.
- [ ] APK روی نصب موجود به‌روزرسانی شده و بدون حذف برنامه نصب شده است.
- [ ] اجرای برنامه، باز شدن صفحهٔ اصلی، کتابخانهٔ حرکات، نمایش GIF و بازگشت به فهرست بررسی شده‌اند.
- [ ] داده‌های قبلی پس از به‌روزرسانی باقی مانده‌اند؛ اگر تغییر پایگاه داده وجود دارد، مهاجرت افزایشی و حفظ داده بررسی شده است.
- [ ] در صورت تغییر ترجمه‌ها، رابط فارسی و انگلیسی جداگانه بررسی شده‌اند.
- [ ] Artifact نهایی را دانلود و با همان فایل بررسی‌شده تطبیق داده‌ای؛ لینک ZIP حاوی metadata را با فایل APK اشتباه نگیر.

## ۶. گزارش انتشار — این بخش را برای هر نسخه تکمیل کن

هر بار نسخهٔ جدید ساخته می‌شود، رکورد تازه‌ای در بالای این جدول اضافه کن:

| مورد | مقدار نسخهٔ جاری |
|---|---|
| نسخه / versionName | در هر انتشار تکمیل شود |
| versionCode | در هر انتشار تکمیل شود |
| commit SHA | SHA دقیق commit ساخته‌شده |
| شناسهٔ بسته | `com.cognitivekernel.androidfit` |
| SHA-256 فایل APK | هش فایل APK دانلودشده |
| SHA-256 گواهی امضا | اثرانگشت signer از `apksigner` |
| CI run و Artifact | لینک اجرای CI و نام دقیق Artifact |
| آزمون نصب روی نسخهٔ قبلی | موفق / ناموفق / انجام‌نشده |
| آزمون GIF و برگشت به فهرست | موفق / ناموفق / انجام‌نشده |
| آزمون فارسی/انگلیسی | موفق / ناموفق / انجام‌نشده |
| وضعیت انتشار | آماده / متوقف؛ علت را بنویس |

**ممنوع:** ثبت «موفق» برای آزمونی که اجرا نشده، ارسال لینک پیش از آماده‌شدن Artifact، استفادهٔ دوباره از versionCode، تغییر بی‌سروصدای کلید امضا، یا اعلام رفع باگ فقط بر اساس افزایش حجم APK.

## ۷. روش تحویل به کاربر

1. فقط Artifact مربوط به commit و نسخه‌ای را ارائه کن که آزمون‌های لازم را گذرانده است.
2. لینک مستقیم صفحهٔ اجرای GitHub Actions یا Release را همراه لینک APK بده.
3. نام دقیق فایل APK، versionName، versionCode، SHA-256 فایل و نتیجهٔ آزمون نصب را اعلام کن.
4. اگر Artifact هنوز در حال ساخت است یا هر بررسی مسدودکننده شکست خورده، صریح بگو لینک نسخهٔ نهایی هنوز آماده نیست.
5. پس از انتشار، همین سند و گزارش نسخه را به‌روزرسانی کن؛ برای انتشار بعدی دوباره از همین چک‌لیست استفاده کن.
